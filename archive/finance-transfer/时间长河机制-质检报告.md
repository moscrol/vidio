## 0. 一句话结论

**机制是真的，不是 PPT。河床修得相当好，但水只流到一半。**

你设计的「点 → 线 → 特征 → 推演」四段里，**前两段已经是可运行的代码契约并通过实测**，第三段有骨架，第四段只接通了一半。真正卡住的不是工程，是**标签词表太小**（注册 17 个、单日可求值 4 个）——这是推演能力的硬天花板。

### 2.2 线状能力 —— 你的核心初衷，部分达成 ⚠️

实跑 15 个交易日的区间，`derive_transitions(market_stage)` 的输出：

```
transitions: [
  {"day":"2026-08-19","from":"震荡","to":"主升","refs":[...]},
  {"day":"2026-08-24","from":"主升","to":"分歧","refs":[...]},
  {"day":"2026-08-26","from":"分歧","to":"主升","refs":[...]},
  ...
]
count: 6     pit_grade: strict     validity_kind: range
```

**这就是你要的「线」**——不是点的罗列，是带日期、带方向、可回溯到源行的状态迁移序列。这条路走通了。

但有三个折扣：

- **`window()` 默认只产 `cumulative` 一类**。另外四类（streak/transition/first_event/signature）必须手工调 `river_derive.*`，不在区间对象里自动挂上。而且实测 `cumulative` 的 `member_refs` 是空的（其他三类都有）。
- **`derive_streak` 对非布尔标签静默返回 0**。我传 `market_stage`（字符串 `'震荡'`），它返回 `longest:0, current:0, status:"ok"`——**不报错、看着像正常读数**。17 个注册标签里只有 `dual_red_strict` 一个是布尔，其余三个可求值标签（`market_stage`/`limit_heat_rank`/`volume_surge`）传进去全是假的 0。
- **`resolve_entity` 只认板块**。指数、题材、个股作为实体入口没开（桥接表 `config_theme_sector_link` 实测 0 行）。所以「六轨 × 多实体」实际是「六轨 × 板块」。

### 2.3 六轨的真实成色

| 轨 | 状态 | 说明 |
|---|---|---|
| 盘面 market | 🟢 最厚 | 指数阶段 + 板块量价 + 涨停热度，3 类对象 |
| 题材 theme | 🟢 | 阶段 + 事件，词表已统一到 v6（七段） |
| 资金 capital | 🟢 | 板块/题材资金流、龙虎榜三表齐 |
| 个股 stock | 🟡 | 只有节点事件，且被 `NODE_LIMIT=10` 截断 |
| 舆论 opinion | 🟠 最弱 | 只能从研报覆盖密度派生；代码注释自曝「402 个板块名里只有 228 个有覆盖」。无社媒热度（设计上刻意不加抓取器） |
| 判断 judgment | 🟡 | 契约完整（三类对象分列），但依赖用户真的在用 |

## 3. 问题清单（按严重度）

### 🔴 P0 — 核心测试在 CI 上永远不执行

四个最重要的测试文件 **整份** 被 `pytestmark = skipif(not DB.exists())` 门掉：

```
tests/test_river_slice.py        （联立契约，21 个用例）
tests/test_river_window.py       （区间契约，8 个）
tests/test_river_query.py        （横扫纵扫）
tests/test_river_cutoff_guard.py （无前视守卫）
```

而 `.gitignore` 第 78–79 行把 `db/` 和 `*.duckdb` 全部排除，GitHub Actions 的 runner 上**不可能有**这个库。

**后果**：AGENTS.md 里那句「全仓 pytest 8010 passed，门禁全绿」**不包含时间长河的核心契约**。这条河的正确性，至今只在你本机验证过。考虑到这个仓已经有过「测试停跑 33 天没人发现」「187 张收据全是收窄读数」的前科，这是同一类风险的新发作点。

**证据**：我今天用 `schema.sql` 造一个能跑通全部契约的最小库只花了约 20 分钟。**这件事可行，只是没做。**

### 🟠 P1 — 标签词表是推演的真实天花板

```
注册标签总数: 17
可单日求值:   4   （dual_red_strict / market_stage / limit_heat_rank / volume_surge）
其中布尔型:   1
```

情景树（`scenario_trees.py`）的分枝条件只收「单日切片可判的注册标签」，规则 DSL 同理。**也就是说，你能用来表达「如果…那么…」的词汇量，目前是 4 个。**

这不是代码问题——引擎（互斥校验、otherwise 强制、max_depth、realized_path 逐日判定）都写好了，而且写得很严谨。是**没有足够的词可以说话**。

### 🟡 P2 — 三维对照实际只有二维

`opinion_stage.dislocation()` 比的是 **题材阶段 × 舆论阶段**，输出 `aligned / opinion_leads / opinion_lags / unverifiable`。

设计文档里那句标志性的「题材在升温验证，舆论还在卖方萌芽，**盘面已连续双红**」——第三维（盘面）没有进这个函数。`environment_script`（环境剧本）对象全仓**零命中**，流动性出口也还没实现。

### 🟡 P3 — 推演与方法论没接上

- `market_regime_analogs.py`（D10 历史相似环境）写得很好：z-score 标准化解决跨年代量纲漂移、缺维降权不伪造、**只报后续 5/10/20 日事实不给概率**。
- `scenario_trees.py`（多步情景树）v0 已落，硬门齐全。

但这两者**和授课框架（你口述的那套方法论）之间还没有连线**。现在的状态是：找得到相似历史窗口，也能画情景树，但「用你的方法去读这个窗口」这一步缺一个 `framework_version` 可钉——因为母本还没定稿。

## 5. 这个实现最值得肯定的地方

读了约 9,200 行 river 相关代码，有一点很罕见：**代码注释里大量自曝其短，而不是粉饰**。几个例子：

- `river.py` 开头：「`updated_at` 是刷新时间……所以整条河的可 strict 段被**系统性低估**。**不要拿别的时刻来补这段低估**」
- `river_query.py` 里的函数注释：「这是补丁不是修复」
- `resolve_entity`：「唯一的桥接表 `config_theme_sector_link` **实测 0 行**。所以只做精确匹配——猜错会静默串轨，比读不出来更糟」
- gap-roadmap 里主动撤回自己的成果：「09-08 撤回：名单时刻证明不了行情内容……那 15 天主动放弃」

**「宁可少算也不多算」「宁可报缺口也不猜」这条纪律，是真的写进了代码分支，不只是写在文档里。** 这在金融类项目里非常少见——大多数实现会在缺数时悄悄填 0。

## 6. 建议（按投入产出排序）

| 优先级 | 动作 | 理由 |
|---|---|---|
| **1** | 把最小夹具库做进 CI | 我 20 分钟就造出来了，可行性已证明。不做的话，这条河的核心契约永远处在「只有一台机器验证过」的状态，而本仓有前科 |
| **2** | `derive_streak` 加类型门 | 非布尔标签应当抛 `LabelNotSliceEvaluable`（这个异常类已经存在），而不是静默返回 0。5 行代码 |
| **3** | **扩标签词表** | 这是解锁推演的唯一杠杆。17 → 40 个标签，情景树的表达力是量级差异。母本骨架 §1.4 里你已经口述出十条旗标，它们的输入字段全在 `fact_market_daily`，缺的只是把阈值填上 |
| **4** | `window()` 默认挂上四类派生 | 现在要手工调，等于区间能力「有但不好用」；顺带修 `cumulative` 的空 `member_refs` |
| **5** | `dislocation()` 补盘面维 | 把二维错位升到三维，这是你设计里最有辨识度的一句话输出 |
| **6** | 开放题材/指数实体入口 | `config_theme_sector_link` 0 行是堵点，但题材轨本身有 `theme_name`，可以先做精确匹配 |

第 3 条是真瓶颈。前两条是工程卫生，一天能做完；第 3 条是你（创始人）的时间，agent 替不了——这一点 roadmap 自己也写对了：「关键路径不是代码，是创始人把课纲写成母本」。
